# Build Orchestrator - Рабочий процесс

## Обзор процесса

Build Orchestrator управляет полным циклом выполнения задач: от получения запроса до финальной проверки качества.

## Шаг 1: Классификация запроса

### Определение типа задачи

Анализ входящего запроса для определения типа:

#### Архитектурные задачи
**Признаки**:
- Требуется проектирование системы или компонента
- Нужно выбрать архитектурный подход или паттерн
- Вовлечены несколько подсистем или сервисов
- Требуется ADR (Architecture Decision Record)

**Агент**: platform-architect или agent-runtime-architect

**Примеры**:
- "Спроектировать микросервис для обработки платежей"
- "Выбрать архитектуру для очереди сообщений"
- "Определить структуру проекта для нового модуля"

#### Задачи реализации
**Признаки**:
- Требуется написать код
- Реализация уже спроектированной функциональности
- Создание новых компонентов или модулей
- Рефакторинг существующего кода

**Агент**: implementation-engineer

**Примеры**:
- "Реализовать REST API для users"
- "Добавить логирование в authentication module"
- "Рефакторить database layer"

#### Интеграционные задачи
**Признаки**:
- Требуется интеграция с внешними сервисами
- Нужно определить контракты интеграции
- Создание адаптеров или мостов между системами
- API design

**Агент**: integration-architect

**Примеры**:
- "Интегрироваться с payment gateway"
- "Создать адаптер для third-party API"
- "Определить контракт для microservice communication"

#### Задачи тестирования
**Признаки**:
- Требуется написать тесты
- Создание тестовой инфраструктуры
- Определение тестовой стратегии

**Агент**: test-engineer

**Примеры**:
- "Написать unit tests для payment module"
- "Создать integration tests для API"
- "Определить тестовую стратегию для нового сервиса"

#### Задачи верификации
**Признаки**:
- Требуется проверка соответствия требованиям
- Валидация архитектуры или реализации
- Проверка качества кода

**Агент**: verification-agent

**Примеры**:
- "Проверить соответствие архитектуры ADR-005"
- "Валидировать реализацию против спецификации"
- "Проверить качество кода перед merge"

### Сложные задачи

Если задача содержит элементы нескольких типов:

1. **Разбить на подзадачи**
   - Каждая подзадача имеет один тип
   - Определить зависимости между подзадачами

2. **Назначить соответствующих агентов**
   - Каждая подзадача - соответствующему агенту
   - Установить порядок выполнения

Пример: "Добавить новый микросервис для отправки email"
- Подзадача 1: Спроектировать архитектуру сервиса (platform-architect)
- Подзадача 2: Определить контракт интеграции (integration-architect)
- Подзадача 3: Реализовать сервис (implementation-engineer)
- Подзадача 4: Написать тесты (test-engineer)
- Подзадача 5: Верифицировать (verification-agent)

## Шаг 2: Создание и приоритизация задач

### Создание задачи

Для каждой задачи создать запись в backlog:

```
## Задача #[ID]

**Тип**: [architecture/implementation/integration/testing/verification]
**Описание**: [Краткое описание]
**Требования**:
- [ ] Требование 1
- [ ] Требование 2
**Зависимости**: [Список ID задач]
**Приоритет**: [Высокий/Средний/Низкий]
**Дедлайн**: [Дата, если есть]
**Оценка времени**: [Часов/Дней]
**QA Gate**: [Что нужно проверить]
**Артефакты**: [Что должно быть создано]
```

### Приоритизация задач

Правила приоритизации:

1. **Блокирующие задачи**
   - Задачи, которые блокируют другие задачи
   - Приоритет: Высокий

2. **Дедлайны**
   - Задачи с близким дедлайном
   - Приоритет: Высокий

3. **Критичность**
   - Задачи, влияющие на стабильность системы
   - Приоритет: Высокий

4. **Обычные задачи**
   - Задачи без блокировок и дедлайнов
   - Приоритет: Средний

5. **Улучшения**
   - Задачи по улучшению кода или документации
   - Приоритет: Низкий

### Сортировка задач

Порядок выполнения:
1. Высокий приоритет
2. Средний приоритет
3. Низкий приоритет

Внутри каждого уровня:
- По дедлайну (ближайшие первыми)
- По зависимостям (зависимости первыми)

## Шаг 3: Назначение агента

### Выбор агента

На основе типа задачи выбрать соответствующего агента:

| Тип задачи | Агент |
|------------|-------|
| Архитектура платформы | platform-architect |
| Архитектура runtime | agent-runtime-architect |
| Реализация кода | implementation-engineer |
| Интеграция | integration-architect |
| Тестирование | test-engineer |
| Верификация | verification-agent |

### Проверка доступности

Перед назначением проверить:
- Агент не занят другой задачей
- Зависимости задачи выполнены
- QA Gate предыдущей задачи пройден

### Назначение задачи

Отправить задание агенту:

```
## Назначена задача: [Краткое описание]

**Тип**: [Тип задачи]
**Приоритет**: [Высокий/Средний/Низкий]
**Описание**: [Полное описание]
**Требования**:
- [ ] Требование 1
- [ ] Требование 2
**Контекст**:
- Ссылки на ADR: [если есть]
- Ссылки на спецификации: [если есть]
- Ссылки на код: [если есть]
**QA Gate**: [Что нужно проверить]
**Дедлайн**: [Дата]
**Ожидаемый результат**: [Что должно быть выполнено]
```

## Шаг 4: Отслеживание прогресса

### Мониторинг выполнения

Проверять прогресс каждые 5-10 минут:

1. **Статус задачи**
   - В работе
   - Завершена
   - Заблокирована
   - Отклонена

2. **Прогресс**
   - Что сделано
   - Что осталось
   - Оценка времени до завершения

3. **Проблемы**
   - Есть ли блокеры
   - Нужна ли помощь
   - Требуется ли эскалация

### Обновление статуса

При изменении статуса обновить backlog:

```
## Задача #[ID] - [Статус]

**Прогресс**: [Что сделано / осталось]
**Артефакты**: [Ссылки на созданные файлы]
**Проблемы**: [Если есть]
**Следующий шаг**: [Что дальше]
```

### Обновление статус-документов

Помимо обновления backlog, агенты должны обновлять статус-документы:

**Обязательные обновления:**
1. **implementation-engineer**: Обновляет `plan.md`, `tasks.md` после завершения фаз
2. **test-engineer**: Обновляет `checklist.md` после завершения тестов
3. **verification-agent**: Обновляет все документы после верификации
4. **code-reviewer**: Обновляет все документы после code review

**Формат обновления** (см. `.specify/templates/status-update-rule.md`):
```markdown
| Date | Agent | Status | Changes | Artifacts | Next Steps |
|------|-------|--------|---------|-----------|-----------|
| [DATE] | [agent-name] | [state] | [description] | [links to files] | [action items] |
```

Build Orchestrator проверяет выполнение обязательных обновлений при переходе между этапами.

### Тайм-ауты

Установить тайм-ауты для каждого типа задачи:

| Тип задачи | Тайм-аут | Действие при тайм-ауте |
|------------|----------|------------------------|
| Архитектура | 2 часа | Эскалировать, предложить помощь |
| Реализация | 4 часа | Проверить прогресс, эскалировать |
| Интеграция | 3 часа | Эскалировать |
| Тестирование | 2 часа | Эскалировать |
| Верификация | 1 час | Эскалировать |

## Шаг 5: Принудительное применение QA Gate

### Проверка QA Gate перед продолжением

Перед тем как задача считается завершенной, проверить:

1. **Для архитектурных задач**
   - ADR создан и записан
   - ADR approved соответствующим архитектором
   - ADR соответствует SPEC.md
   - Все рассмотренные альтернативы задокументированы

2. **Для задач реализации**
   - Код соответствует ADR
   - Код соответствует code standards
   - Код протестирован
   - Документация создана

3. **Для интеграционных задач**
   - Контракт интеграции определен
   - ADR для контракта создан и approved
   - Реализация соответствует контракту

4. **Для задач тестирования**
   - Тесты покрывают требования
   - Тесты проходят
   - Тестовая документация создана

5. **Для задач верификации**
   - Все проверки выполнены
   - Соответствие требованиям подтверждено
   - Проблемы задокументированы

### Отклонение при непрохождении QA Gate

Если QA Gate не пройден:

```
❌ Задача #[ID] отклонена

**Причина отклонения**:
- [ ] QA Gate 1 не пройден: [описание]
- [ ] QA Gate 2 не пройден: [описание]

**Требуемые исправления**:
- [ ] Исправление 1
- [ ] Исправление 2

**Дедлайн**: [Дата]
**Переназначено**: [Агент]
```

## Шаг 6: Управление статус-документами

### Обновление Status Index

Build Orchestrator отвечает за обновление Status Index (`docs/STATUS.md`):

**Когда обновлять Status Index:**
- После завершения каждой фазы проекта
- После создания новых статус-документов
- После значительных изменений в статусах компонентов
- Раз в неделю для регулярной синхронизации

**Формат обновления:**
```markdown
## 📈 Метрики прогресса

- **Завершено:** [X]/[Y] компонентов (Z%)
- **В работе:** [A]/[Y] компонентов (B%)
- **В планах:** [C]/[Y] компонентов (C%)
```

**Статусы компонентов:**
- ✅ Завершен (100%)
- 🔄 В разработке (1-99%)
- 📋 В планах (0%)
- ❌ Заблокирован
- ⚠️ Отложен

### Координация обновлений статус-документов

Build Orchestrator координирует обновления от других агентов:

| Агент | Обновляет | Когда |
|-------|-----------|-------|
| implementation-engineer | plan.md, tasks.md | После завершения фаз |
| test-engineer | checklist.md | После завершения тестов |
| verification-agent | Все документы | После верификации |
| code-reviewer | Все документы | После code review |
| build-orchestrator | Status Index | После завершения фазы проекта |

### Мониторинг соответствия статус-документов

Проверять, что все агенты следуют правилам обновления статусов:

**Чек-лист проверки:**
- [ ] Все шаблоны имеют секции статуса (plan.md, tasks.md, spec.md, checklist.md)
- [ ] Агенты обновляют статус после завершения работы
- [ ] Формат статусов соответствует `status-update-rule.md`
- [ ] Ссылки на артефакты корректны
- [ ] Следующие шаги указаны явно

**Если нарушения обнаружены:**
```markdown
⚠️ Нарушение правил обновления статуса

**Агент**: [имя агента]
**Файл**: [путь к файлу]
**Нарушение**: [описание]
**Требуемое действие**: [что нужно сделать]
```

### Эскалация проблем со статусами

Условия для эскалации:

1. **Статус заблокирован более 30 минут**
   - Действие: Связаться с агентом, предложить помощь
   - Если не решается в 15 минут: эскалировать владельцу задачи

2. **Многократные ошибки статуса**
   - >3 `retry_on_error` или `failed` подряд
   - Действие: Провести анализ причин, изменить подход

3. **Несоответствие статуса реальному прогрессу**
   - Статус `completed` но артефакты отсутствуют
   - Статус `in_progress` но активность отсутствует >1 час
   - Действие: Запросить обновление, скорректировать статус

4. **Отсутствие обязательных обновлений**
   - Агент не обновил статус после завершения работы
   - Действие: Напомнить агенту, обновить самостоятельно
   - Если повторяется: Добавить в QA Gate как обязательное требование

### Обновление Status Index

Процедура обновления Status Index (`docs/STATUS.md`):

1. **Собрать информацию:**
   - Статусы всех компонентов
   - Прогресс по фазам проекта
   - Новые созданные документы
   - Блокирующие проблемы

2. **Обновить YAML front matter:**
   ```yaml
   ---
   title: Project Status Index
   version: [increment version]
   last_updated: [YYYY-MM-DD]
   owner: py-symphony team
   status: active
   ---
   ```

3. **Обновить таблицы:**
   - Общий статус компонентов
   - Детальные документы (если добавились новые)
   - Метрики прогресса

4. **Обновить ссылки:**
   - Добавить новые документы в соответствующие секции
   - Проверить корректность существующих ссылок

5. **Записать изменения:**
   ```markdown
   ---
   *Обновлено: [YYYY-MM-DD] | Автор: build-orchestrator*
   ```

## Шаг 7: Координация handoff

### Подготовка к передаче

Перед передачей задачи следующему агенту:

1. **Собрать все артефакты**
   - ADR (если есть)
   - Код
   - Тесты
   - Документация
   - Результаты verification

2. **Подготовить контекст**
   - Краткое описание того, что было сделано
   - Ссылки на все артефакты
   - Зависимости от других задач

3. **Проверить QA Gate**
   - Все QA Gates пройдены
   - Результаты verification положительные

### Передача задачи

```
## Передача задачи: [Краткое описание]

**От**: [Предыдущий агент]
**Кому**: [Следующий агент]

**Что было сделано**:
- [ ] Этап 1: [результат]
- [ ] Этап 2: [результат]

**Артефакты**:
- ADR: [ссылка]
- Код: [ссылка]
- Тесты: [ссылка]
- Документация: [ссылка]
- Verification: [ссылка]

**Следующие шаги**:
- [ ] Шаг 1
- [ ] Шаг 2

**QA Gate для следующего этапа**: [Что нужно проверить]
```

### Принятие задачи

Агент принимает задачу:

```
## Задача принята

**Задача**: [ID и описание]
**Агент**: [Имя агента]
**Понято**: [Краткое подтверждение понимания]
**План выполнения**:
1. [Шаг 1]
2. [Шаг 2]

**Вопросы**: [Если есть]
```

### Отклонение задачи

Агент отклоняет задачу:

```
## Задача отклонена

**Задача**: [ID и описание]
**Агент**: [Имя агента]
**Причина отклонения**: [Почему]
**Требуемые исправления**:
- [ ] Исправление 1
- [ ] Исправление 2
```

## Завершение процесса

### Успешное завершение

Когда все QA Gates пройдены:

```
✅ Задача #[ID] завершена успешно

**Результат**: [Что было выполнено]
**Артефакты**:
- [ ] ADR: [ссылка]
- [ ] Код: [ссылка]
- [ ] Тесты: [ссылка]
- [ ] Документация: [ссылка]
- [ ] Verification: [ссылка]

**QA Gates**: Все пройдены ✅
**Следующая задача**: [Если есть]
```

### Финальная проверка

Перед закрытием задачи:

1. Проверить все артефакты
2. Убедиться, что все QA Gates пройдены
3. Проверить, что нет блокировок для других задач
4. Обновить статус задачи в backlog
5. Передать следующую задачу соответствующему агенту
6. Проверить, что все статус-документы обновлены
7. Обновить Status Index (`docs/STATUS.md`) с текущим прогрессом
