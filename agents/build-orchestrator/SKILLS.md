# Build Orchestrator - Навыки (Skills)

## Обзор

Build Orchestrator использует следующие навыки для эффективного выполнения своих обязанностей.

## Навык: Управление задачами (Task Management)

### Описание
Способность создавать, отслеживать и управлять задачами на протяжении всего жизненного цикла: от создания до завершения.

### Компоненты навыка

#### 1. Создание задач
- Разбивка сложных запросов на подзадачи
- Определение типа каждой задачи
- Определение зависимостей между задачами
- Установка приоритетов и дедлайнов
- Создание полного описания с требованиями

#### 2. Отслеживание состояния
- Мониторинг статуса всех активных задач
- Обновление состояния при изменениях
- Логирование прогресса и проблем
- Определение задержек и блокировок

#### 3. Управление зависимостями
- Определение порядка выполнения на основе зависимостей
- Блокирование задач, чьи зависимости не выполнены
- Разблокирование задач при выполнении зависимостей
- Управление циклическими зависимостями

#### 4. Завершение задач
- Проверка всех QA Gates
- Сбор и верификация всех артефактов
- Обновление статуса задачи
- Подготовка отчета о выполнении

### Примеры использования

```
## Создание задачи
Вход: "Добавить новый microservice для email notifications"
Действия:
1. Разбить на 5 подзадач:
   - Архитектура (platform-architect)
   - Контракт интеграции (integration-architect)
   - Реализация (implementation-engineer)
   - Тесты (test-engineer)
   - Верификация (verification-agent)
2. Определить зависимости:
   - Тесты зависят от реализации
   - Верификация зависит от тестов
3. Установить приоритеты:
   - Архитектура: Высокий
   - Остальные: Средний

## Отслеживание состояния
Каждые 5-10 минут:
- Проверить статус каждой задачи
- Обновить прогресс
- Логировать проблемы
- Проверить дедлайны
```

## Навык: Приоритизация (Prioritization)

### Описание
Способность определять порядок выполнения задач на основе множества факторов: критичности, дедлайнов, зависимостей, доступности ресурсов.

### Компоненты навыка

#### 1. Определение приоритетов
- Оценка критичности для проекта
- Учет дедлайнов
- Анализ влияния на другие задачи
- Учет доступности агентов

#### 2. Динамическая реприоритизация
- Пересмотр приоритетов при изменении условий
- Реакция на новые задачи с высоким приоритетом
- Корректировка при изменении дедлайнов
- Адаптация при изменении доступности агентов

#### 3. Управление конфликтами приоритетов
- Разрешение конфликтов между задачами
- Определение приоритетов при ограниченных ресурсах
- Принятие решений о задержке менее критичных задач

### Матрица приоритетов

| Критичность | Дедлайн близкий | Дедлайн далеко |
|--------------|-----------------|----------------|
| Высокая     | КРИТИЧЕСКИЙ     | Высокий        |
| Средняя     | Высокий         | Средний        |
| Низкая      | Средний         | Низкий         |

### Примеры использования

```
## Определение приоритетов
Задача 1: Исправление бага в production
- Критичность: Высокая
- Дедлайн: Сегодня
- Приоритет: КРИТИЧЕСКИЙ

Задача 2: Рефакторинг кода
- Критичность: Низкая
- Дедлайн: Через месяц
- Приоритет: Низкий

Задача 3: Новый feature для клиента
- Критичность: Средняя
- Дедлайн: Через неделю
- Приоритет: Высокий

## Динамическая реприоритизация
Ситуация: Поступил критический баг в production
Действия:
1. Остановить текущие задачи с низким приоритетом
2. Перенести критический баг на первое место
3. Оценить влияние на дедлайны других задач
4. Уведомить агентов об изменении приоритетов
```

## Навык: Координация коммуникации (Communication Coordination)

### Описание
Способность эффективно координировать коммуникацию между агентами, обеспечивая ясность, точность и своевременность передачи информации.

### Компоненты навыка

#### 1. Формирование сообщений
- Структурирование информации
- Использование стандартных шаблонов
- Указание ясных ожиданий
- Предоставление полного контекста

#### 2. Обеспечение понимания
- Проверка, что агент понял задачу
- Уточнение требований при необходимости
- Ответ на вопросы агентов
- Предоставление дополнительной информации

#### 3. Координация handoffs
- Подготовка артефактов для передачи
- Обеспечение полного контекста
- Проверка QA Gates перед передачей
- Обработка отклонений

#### 4. Эскалация проблем
- Определение триггеров эскалации
- Подготовка ясного описания проблемы
- Указание требуемого действия
- Установка дедлайна для решения

### Шаблоны коммуникации

#### Назначение задачи
```
## Назначена задача: [Краткое описание]

**Тип**: [Тип задачи]
**Приоритет**: [Высокий/Средний/Низкий]
**Дедлайн**: [Дата]

**Описание**: [Полное описание]
**Требования**:
- [ ] Требование 1
- [ ] Требование 2

**Контекст**:
- Ссылки на ADR: [если есть]
- Ссылки на спецификации: [если есть]
- Связанные задачи: [ID задач]

**QA Gate**: [Что нужно проверить]
**Ожидаемый результат**: [Что должно быть выполнено]
```

#### Эскалация
```
## 🚨 Эскалация

**Тип**: [Тип проблемы]
**Задача**: [ID задачи]
**Агент**: [Имя агента]

**Проблема**: [Описание]
**Влияние**: [Как влияет на проект]
**Время блокировки**: [Сколько прошло]

**Требуемое действие**: [Что нужно сделать]
**Дедлайн**: [Когда нужно решить]
```

### Примеры использования

```
## Формирование сообщения
Задача: Реализовать payment service
Результат:
"## Назначена задача: Реализовать PaymentService

**Тип**: Реализация
**Приоритет**: Высокий
**Дедлайн**: 2024-04-15

**Описание**: Реализовать PaymentService согласно ADR-001
**Требования**:
- [ ] PaymentService с методами: processPayment, getStatus, refund
- [ ] Поддержка 3 providers: Stripe, PayPal, Adyen
- [ ] Unit tests для всех методов

**Контекст**:
- ADR-001: [ссылка]
- Code standards: PEP 8
- Связанные задачи: #125 (тесты)

**QA Gate**: verification-agent проверит соответствие ADR-001
**Ожидаемый результат**: Код в PR, тесты, coverage > 80%"

## Обеспечение понимания
Агент: "Нужно ли реализовать retry logic для providers?"
Ответ: "Да, ADR-001 требует retry logic с экспоненциальным backoff.
Смотри раздел 3.2 ADR-001. Максимальное количество попыток: 3."
```

## Навык: Отслеживание прогресса (Progress Tracking)

### Описание
Способность систематически отслеживать прогресс выполнения задач, выявлять проблемы и своевременно реагировать на задержки.

### Компоненты навыка

#### 1. Мониторинг статусов
- Регулярная проверка статуса задач
- Обновление прогресса
- Логирование изменений
- Определение тенденций

#### 2. Выявление проблем
- Определение блокировок
- Выявление задержек
- Распознание повторяющихся проблем
- Анализ причин проблем

#### 3. Прогнозирование
- Оценка времени до завершения
- Прогнозирование потенциальных проблем
- Предупреждение о возможных задержках

#### 4. Реакция на проблемы
- Предложение решений
- Эскалация при необходимости
- Переназначение задач
- Корректировка планов

### Интервалы мониторинга

| Тип задачи | Интервал проверки | Тайм-аут |
|------------|-------------------|----------|
| Архитектура | 10 минут | 2 часа |
| Реализация | 5 минут | 4 часа |
| Интеграция | 5 минут | 3 часа |
| Тестирование | 5 минут | 2 часа |
| Верификация | 5 минут | 1 час |

### Примеры использования

```
## Мониторинг статусов
Задача #123: Реализация PaymentService
- 14:00 - Назначена implementation-engineer
- 14:10 - В работе: создан service.py
- 14:20 - В работе: создан providers/
- 14:30 - В работе: написаны unit tests
- 14:40 - Прогресс: 80%, ожидается завершение через 10 мин
- 14:50 - Завершена ✅

## Выявление проблем
Задача #124: Тесты PaymentService
- 15:00 - Назначена test-engineer
- 15:30 - Прогресс: 20%
- 16:00 - Прогресс: 30% (задержка!)
- 16:05 - Запрос у агента: "Есть ли проблемы?"
- 16:10 - Ответ: "Сложно настроить test fixtures"
- 16:15 - Предложение решения: "Использовать pytest-mock"
- 16:30 - Прогресс: 60%

## Прогнозирование
Задача #125: Интеграция PaymentService
- Текущий прогресс: 40%
- Время выполнения: 30 минут
- Оценка оставшегося времени: 45 минут
- Прогноз завершения: 17:45
- Дедлайн: 18:00
- Вывод: Будет выполнена вовремя ✅
```

## Комбинирование навыков

### Пример полного сценария

```
## Сценарий: Новый microservice для email notifications

### Шаг 1: Управление задачами
- Получен запрос: "Добавить email notification service"
- Разбивка на 5 подзадач
- Определение зависимостей
- Создание записей в backlog

### Шаг 2: Приоритизация
- Оценка критичности: Средняя
- Дедлайн: Через 2 недели
- Приоритет: Средний

### Шаг 3: Координация коммуникации
- Назначение первой задачи platform-architect
- Предоставление полного контекста
- Указание QA Gate: ADR должен быть approved

### Шаг 4: Отслеживание прогресса
- Мониторинг каждые 10 минут
- Прогресс: 20% → 50% → 80% → 100%
- Задача завершена ✅

### Шаг 5: Приоритизация (динамическая)
- Следующая задача: integration-architect
- Проверка: зависимость выполнена (ADR создан)
- Продолжение workflow

### Шаг 6: Координация коммуникации (handoff)
- Подготовка arфacts (ADR)
- Передача integration-architect
- Указание QA Gate: контракт должен соответствовать ADR

### И так далее для всех 5 задач...
```

## Метрики эффективности

Для оценки эффективности Build Orchestrator используются следующие метрики:

1. **Время создания задачи**: Время от получения запроса до назначения задачи
   - Цель: < 5 минут

2. **Время ответа на вопросы агентов**: Время от вопроса до ответа
   - Цель: < 10 минут

3. **Время реакции на проблемы**: Время от выявления проблемы до начала решения
   - Цель: < 15 минут

4. **Время завершения workflow**: Время от первой до последней задачи
   - Зависит от сложности, но должно быть оптимизировано

5. **Количество эскалаций**: Должно быть минимальным
   - Цель: < 10% задач требуют эскалации

6. **Удовлетворенность агентов**: Субъективная оценка агентами качества коммуникации
   - Цель: > 4/5
