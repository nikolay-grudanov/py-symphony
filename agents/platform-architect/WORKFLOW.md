# Процесс работы: Platform Architect

## Шаг 1: Анализ требований

### Цель

Понять бизнес-требования и технические ограничения, которые влияют на архитектуру.

### Действия

1. **Сбор требований**
   - Получить функциональные требования от заинтересованных сторон
   - Получить нефункциональные требования (производительность, надежность, безопасность)
   - Определить ограничения (бюджет, время, команда)

2. **Анализ существующей архитектуры**
   - Изучить SPEC.md для понимания архитектурных компонентов и слоев
   - Проанализировать существующие ADR
   - Изучить существующие архитектурные диаграммы

3. **Выявление критических факторов**
   - Определить наиболее важные нефункциональные требования
   - Выявить критические зависимости и ограничения
   - Определить области наибольшего риска

### Выходные данные

- Понятные требования к архитектуре
- Анализ существующей архитектуры
- Список критических факторов успеха

---

## Шаг 2: Оценка технологий

### Цель

Оценить альтернативные технологии и выбрать подходящий стек для каждого компонента.

### Действия

1. **Определение технологических потребностей**
   - Определить требования к технологиям для каждого компонента
   - Выявить критерии оценки (производительность, надежность, совместимость)
   - Определить ограничения на выбор технологий

2. **Поиск альтернатив**
   - Идентифицировать альтернативные технологии для каждого компонента
   - Собрать информацию о каждой альтернативе
   - Определить возможности интеграции между технологиями

3. **Сравнительный анализ**
   - Сравнить альтернативы по определенным критериям
   - Провести пилотное тестирование, если необходимо
   - Оценить долгосрочную жизнеспособность каждой альтернативы

### Выходные данные

- Матрица сравнения технологий
- Рекомендации по выбору технологий
- Обоснование выбора каждой технологии

---

## Шаг 3: Проектирование архитектуры

### Цель

Создать архитектуру, которая соответствует требованиям и использует выбранные технологии.

### Действия

1. **Высокоуровневое проектирование**
   - Определить основные компоненты и их ответственность
   - Определить слои архитектуры (Policy Layer, Configuration Layer, Coordination Layer, Execution Layer, Integration Layer, Observability Layer)
   - Определить паттерны взаимодействия между компонентами

2. **Детализация компонентов**
   - Специфицировать интерфейсы каждого компонента
   - Определить внутреннюю структуру каждого компонента
   - Определить зависимости между компонентами

3. **Проектирование данных**
   - Определить модели данных для каждого компонента
   - Определить форматы обмена данными
   - Определить стратегии сохраняемости и миграции данных

4. **Проектирование интеграций**
   - Определить интеграционные интерфейсы для Issue Tracker Client (Linear)
   - Определить интеграционные интерфейсы для Agent Runner (Codex app-server)
   - Определить контракты для других внешних систем

### Выходные данные

- Архитектурные диаграммы компонентов
- Спецификации компонентов
- Модели данных и контракты интеграции

---

## Шаг 4: Создание ADR (Architecture Decision Records)

### Цель

Документировать архитектурные решения в явном и структурированном виде.

### Действия

1. **Идентификация решений**
   - Составить список всех архитектурных решений
   - Приоритизировать решения по влиянию на архитектуру
   - Определить взаимозависимости между решениями

2. **Документирование каждого решения**
   - Создать ADR для каждого значимого решения
   - Включить в ADR: контекст, решение, обоснование, альтернативы, последствия
   - Связать ADR с соответствующими диаграммами и спецификациями

3. **Обзор и утверждение**
   - Провести обзор ADR с заинтересованными сторонами
   - Получить обратную связь и внести изменения
   - Утвердить финальные ADR

### Выходные данные

- Набор утвержденных ADR
- Краткий обзор всех архитектурных решений
- Связи между ADR и другими артефактами архитектуры

---

## Шаг 5: Обзор и итерация

### Цель

Проверить архитектуру на соответствие требованиям и внести необходимые изменения.

### Действия

1. **Архитектурный обзор**
   - Проверить архитектуру на соответствие требованиям
   - Проверить архитектуру на согласованность и непротиворечивость
   - Проверить архитектуру на реализуемость

2. **Оценка рисков**
   - Идентифицировать риски архитектуры
   - Оценить вероятность и влияние каждого риска
   - Определить стратегии смягчения рисков

3. **Итерация**
   - Внести изменения в архитектуру на основе обзора
   - Обновить ADR и диаграммы
   - Повторить обзор, если необходимо

### Выходные данные

- Обзор архитектуры
- Оценка рисков
- Обновленные ADR и диаграммы

---

## Контракты передачи работы

### Передача implementation-engineer

**Что передается:**
- Спецификации компонентов (Workflow Loader, Config Layer, Issue Tracker Client, Orchestrator, Workspace Manager, Agent Runner)
- API контракты между компонентами
- Контракты интеграции с внешними системами
- Технологический стек для каждого компонента

**В каком формате:**
- Файлы спецификаций в формате Markdown
- UML диаграммы компонентов и их взаимодействий
- Примеры интерфейсов и контрактов

### Передача workflow-architect

**Что передается:**
- Требования к процессам Workflow Loader
- Требования к WORKFLOW.md контракту
- Архитектурные ограничения на процессы
- Контракты для взаимодействия процессов с компонентами

**В каком формате:**
- Файлы требований в формате Markdown
- Схемы процессов
- Контракты в формате Markdown или JSON

### Передача integration-architect

**Что передается:**
- Контракты интеграции для Issue Tracker Client (Linear)
- Контракты интеграции для Agent Runner (Codex app-server)
- Архитектурные ограничения на интеграции
- Требования к безопасности интеграций

**В каком формате:**
- Файлы контрактов в формате Markdown
- Примеры запросов/ответов для API
- Схемы данных для интеграций

### Передача verification-agent

**Что передается:**
- Критерии валидации архитектуры
- Контракты для проверки реализаций
- Метрики для оценки качества архитектуры
- Критерии приемки для компонентов

**В каком формате:**
- Файлы критериев в формате Markdown
- Чек-листы валидации
- Определения метрик

## Итерационный процесс

### Цикл итерации

1. **Планирование итерации**
   - Определить цели итерации
   - Определить время и ресурсы для итерации
   - Установить критерии завершения итерации

2. **Выполнение итерации**
   - Выполнить шаги 1-5 процесса
   - Документировать промежуточные результаты
   - Собрать обратную связь

3. **Оценка итерации**
   - Оценить выполнение целей итерации
   - Идентифицировать улучшения для следующей итерации
   - Обновить планы и документацию

4. **Корректировка архитектуры**
   - Внести изменения в архитектуру на основе оценки
   - Обновить ADR и диаграммы
   - Повторить цикл, если необходимо

### Условия завершения

Архитектура считается завершенной, когда:

- Все критические требования удовлетворены
- Все архитектурные решения документированы в ADR
- Все компоненты специфицированы
- Все контракты определены
- Все риски оценены и стратегии смягчения определены

---

## Мониторинг и поддержание архитектуры

### Регулярный обзор

- Проводить регулярный обзор архитектуры (например, раз в квартал)
- Проверять соответствие архитектуры новым требованиям
- Обновлять ADR и диаграммы при изменениях

### Обработка изменений

- Оценивать влияние изменений на архитектуру
- Обновлять архитектуру при необходимости
- Документировать изменения в новых или существующих ADR

### Обучение и распространение

- Обучать команду архитектуре
- Создавать справочники по архитектуре
- Делиться архитектурными решениями с другими командами
