# Разрешенные навыки: Platform Architect

## Общий принцип

Агент platform-architect может использовать только навыки, перечисленные в этом документе. Каждый навык определяется своей целью, входными данными, выходными данными и условиями использования.

---

## architecture-design

### Цель

Систематическое проектирование архитектуры системы для Symphony Service.

### Когда используется

Используется для проектирования архитектуры новых компонентов, систем или целой платформы.

### Входные данные

- Требования к системе (функциональные и нефункциональные)
- Ограничения (технические, бюджетные, организационные)
- Контекст (существующая архитектура, текущие технологии)
- Существующие артефакты (SPEC.md, ADR, диаграммы)

### Выходные данные

- Архитектурные диаграммы (component diagrams, deployment diagrams, sequence diagrams)
- Спецификации компонентов
- Модели данных
- Архитектурные решения (ADR)

### Как использовать

1. Определить цели и область проектирования
2. Анализировать требования и контекст
3. Создать высокоуровневую архитектуру
4. Детализировать архитектуру по слоям и компонентам
5. Документировать решения в ADR
6. Создать архитектурные диаграммы
7. Проверить архитектуру на соответствие требованиям

---

## architecture-review

### Цель

Проверка существующей архитектуры на соответствие требованиям и выявление проблем.

### Когда используется

Используется для проверки существующей архитектуры, оценки предлагаемых изменений или валидации архитектурных решений.

### Входные данные

- Существующая архитектура (диаграммы, спецификации, ADR)
- Требования к системе
- Контекст изменений (если оценивается изменение)
- Критерии валидации

### Выходные данные

- Отчет о проверке архитектуры
- Список выявленных проблем
- Рекомендации по улучшению
- Решение: принять/отклонить/изменить архитектуру

### Как использовать

1. Определить цели проверки
2. Изучить существующую архитектуру
3. Проверить архитектуру на соответствие требованиям
4. Проверить архитектуру на согласованность
5. Проверить архитектуру на реализуемость
6. Идентифицировать проблемы и риски
7. Создать рекомендации по улучшению
8. Документировать результаты проверки

---

## system-modeling

### Цель

Создание моделей системы для различных целей (данные, поведение, deployment).

### Когда используется

Используется для моделирования различных аспектов системы, таких как модели данных, модели поведения, модели развертывания.

### Входные данные

- Требования к модели (какие аспекты нужно моделировать)
- Контекст моделирования (существующие модели, ограничения)
- Целевая аудитория модели (кто будет использовать модель)

### Выходные данные

- Модели данных (ER diagrams, data flow diagrams)
- Модели поведения (state machine diagrams, activity diagrams)
- Модели развертывания (deployment diagrams, infrastructure diagrams)
- Описание моделей в текстовом виде

### Как использовать

1. Определить цели моделирования
2. Выбрать типы моделей, которые нужны
3. Создать модели данных
4. Создать модели поведения
5. Создать модели развертывания
6. Проверить модели на полноту и согласованность
7. Документировать модели

---

## technology-selection

### Цель

Выбор технологий для реализации архитектурных решений.

### Когда используется

Используется для выбора технологий для новых компонентов, для оценки альтернативных технологий или для миграции на новые технологии.

### Входные данные

- Требования к технологии (функциональные и нефункциональные)
- Ограничения (совместимость, команда, бюджет)
- Контекст (существующие технологии, инфраструктура)
- Альтернативные технологии

### Выходные данные

- Анализ альтернативных технологий
- Рекомендация по выбору технологии
- Обоснование выбора
- План внедрения технологии

### Как использовать

1. Определить требования к технологии
2. Идентифицировать альтернативные технологии
3. Собрать информацию о каждой альтернативе
4. Сравнить альтернативы по критериям
5. Провести пилотное тестирование, если необходимо
6. Оценить долгосрочную жизнеспособность
7. Выбрать оптимальную технологию
8. Документировать решение в ADR

## Ограничения на использование навыков

### Последовательность использования

1. **architecture-review** должен использоваться перед **architecture-design**, если проверяется существующая архитектура
2. **architecture-design** должен использоваться перед **system-modeling** для создания моделей на основе архитектуры
3. **technology-selection** должен использоваться в рамках **architecture-design** или отдельно для выбора технологий
4. **architecture-review** должен использоваться после **architecture-design** для проверки созданной архитектуры

### Обязательные комбинации

- **architecture-design** + **system-modeling**: для создания архитектуры и моделей
- **architecture-design** + **technology-selection**: для создания архитектуры с выбором технологий
- **architecture-review** + **architecture-design**: для проверки существующей архитектуры и создания улучшений

### Необязательные комбинации

- **technology-selection** + **architecture-review**: для оценки технологий в контексте архитектуры
- **system-modeling** + **architecture-review**: для проверки моделей в контексте архитектуры

## Интеграция с WORKFLOW.md

### Соответствие шагам WORKFLOW.md

1. **Шаг 1: Анализ требований**
   - Использовать **architecture-review** для анализа существующей архитектуры
   - Собрать требования для архитектурного проектирования

2. **Шаг 2: Оценка технологий**
   - Использовать **technology-selection** для оценки альтернативных технологий
   - Создать рекомендации по выбору технологий

3. **Шаг 3: Проектирование архитектуры**
   - Использовать **architecture-design** для создания архитектуры
   - Использовать **system-modeling** для создания моделей

4. **Шаг 4: Создание ADR**
   - Использовать **architecture-design** для документирования решений
   - Создать ADR для каждого значимого решения

5. **Шаг 5: Обзор и итерация**
   - Использовать **architecture-review** для проверки архитектуры
   - Итеративно улучшать архитектуру на основе обзора

## Метрики использования навыков

### Ожидаемая частота использования

- **architecture-design**: высокая (для каждого нового компонента или системы)
- **architecture-review**: высокая (для проверки существующей архитектуры)
- **system-modeling**: средняя (для создания моделей по мере необходимости)
- **technology-selection**: средняя (для выбора технологий при необходимости)

### Ожидаемое время выполнения

- **architecture-design**: несколько часов для сложной архитектуры
- **architecture-review**: несколько часов для проверки сложной архитектуры
- **system-modeling**: несколько часов для создания комплексных моделей
- **technology-selection**: несколько часов для оценки нескольких альтернатив

### Критерии успешного использования

- **architecture-design**: создана согласованная архитектура, все решения документированы в ADR
- **architecture-review**: выявлены все проблемы, предоставлены рекомендации
- **system-modeling**: созданы полные и согласованные модели
- **technology-selection**: выбрана оптимальная технология, решение документировано в ADR
